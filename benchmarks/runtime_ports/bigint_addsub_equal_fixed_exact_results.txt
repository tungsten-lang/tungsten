BIGINT POSITIVE EQUAL-WIDTH ADD@{2,4,8,16,24} AND SUB@{2,3,4,8,16,24}
EXACT SOURCE CHECKPOINT
=====================================================================

Scope
-----

This checkpoint ports the remaining positive equal-width fixed-kernel
add/sub leaves from C to native Tungsten, completing the equal-width family
that the earlier add@3 checkpoint opened:

  * add@2   — bigint_add_two_limb_magnitudes' same-sign arm (exact class-four
              hot take, two limb sums with explicit carries, unconditional
              third-limb publication, size two or three);
  * add@4, add@8, add@16, add@24 — bigint_add_equal_fast's fixed arms: the
              literal AArch64 bn_add{4,8,16,24}_fixed load/add-with-carry/
              store schedules, the hot take in the power-of-two class of N+1
              limbs (8, 16, 32, 32), an unconditional carry-limb store, and a
              normalized size of N or N+1;
  * sub@2   — bigint_add_two_limb_magnitudes' opposite-sign arm (two-limb
              compare, larger minus smaller, C's one-limb demotion or exact
              two-limb publication);
  * sub@3, sub@4, sub@8, sub@16, sub@24 — bigint_sub_any's boxed equal-width
              route into bigint_sub_equal_fast: the top-limb compare with the
              full descending scan on a tie, the hot take in N's smallest-fit
              class (4, 4, 8, 16, 32), the literal bn_sub{3,4,8,16,24}_fixed
              schedule over larger minus smaller, then C's exact top-limb
              publication or trim-and-demote finisher.

Every kernel schedule was generated from, and verified token-for-token
against, the C text in runtime/runtime.c (the generator's instruction list
equals the BN_FIXED_ADDSUB / BN_FIXED_ADDSUB24 expansion for each width).
Negative operands, mixed signs, `x - x` (C's O(1) identity), every other
equal width (5..7, 9..15, 17..23, and 32 and above, which carry C's
page-rehome hazard guard), unequal widths, and open-world BigInt#+ /
BigInt#- replacements retain their previous routes. The add@3 leaf,
retained by the previous checkpoint, is now always-inlined into the +
worker (see "add@3" below). This is the exact-port checkpoint; no
native-only arithmetic redesign is included.

Retained dispatch (ten candidates were measured to reach it)
------------------------------------------------------------

  * Runtime gate `bigint_src_shape` (runtime.c). It runs on EVERY
    w_add/w_sub bigint pair, including the typed harness lanes, which reach
    it through `__w_add_fast`/`__w_sub_fast`. The add lines that predate
    this checkpoint keep their exact text and order, followed by one bit
    test admitting widths 2, 4, 8, 16, 24. The sub side is one `sb == 1`
    word-shape branch with a range test (replacing an eight-line chain),
    then one bit test admitting widths 2, 3, 4, 8, 16, 24 with `a != b`.
    Rejected forms: seven extra equal-width lines ahead of the word line
    (unchanged sub1@4 4.4 -> 6.2 ns, sub@5 5.9 -> 7.9 ns); the word branch
    ahead of the add lines (add@3 1.06-1.07); a branch-free predicate
    ahead of everything (add@3 1.01-1.08 under load, no better); the
    admissions folded into the equal-length exclusion block (add@5 1.081
    and sub@4 1.071, both 0/31 wins).
  * `+` worker: after the scalar-word case, `an == bn` then direct compares
    for widths 3 and 2, then `(an & 3) == 0` ahead of a switch over 4, 8,
    16, 24. A six-way switch alone lowered to a compare cluster that cost
    add@3 6% against its former single compare.
  * `-` worker: the scalar-word chain of eight `an == N && bn0 == 1`
    compares became one `bn0 == 1` test with a width switch, mirroring +;
    the equal-width leaves are one switch over 2, 3, 4, 8, 16, 24. Two
    direct compares ahead of that switch measured 8-13% on sub@4/8/16
    (2-5 wins of 21 in two rounds), while the switch alone held parity.
  * add@3 leaf `; tungsten:alwaysinline`. With everything else identical,
    add@3 measured 1.056 (3/21) against baseline: its gate and worker
    paths are instruction-identical, only w_add's block placement moved
    (the shared return block sits 0x1d4 bytes further). Inlining the
    ten-instruction leaf removes its call/return pair and puts the cell at
    1.007 (11/31) with add1@1/4/16 at 0.99/0.99/0.98.

Method
------

Alternating process pairs of the two harness binaries: each leg is
`bench_big_math_tungsten_native --sweep OP LIMBS 3 300` (min of three
warmed samples), baseline-then-candidate on even pairs and the reverse on
odd pairs, every leg under `taskpolicy -c utility -t 0 -l 0` (the repo's
bench_pinned.sh tier); the verdict is the median paired ratio
candidate/baseline. Every leg checks its cell against the C oracle before
timing.

Null controls (baseline against a byte-identical copy of itself, 21 pairs):
wall clock add@3 0.9988 (IQR 0.042), add@5 0.9944 (0.031); QoS wall clock
add@3 0.9898 (0.063), sub@4 1.0087 (0.060); QoS CPU clock add@3 0.9699
(0.049), sub@4 0.9922 (0.037). The method is unbiased to within its
+/-3-5% per-cell noise floor at this load; the CPU clock removes the
preemption component and is used for the final tables.

add@5 is the one row over the 5% budget, and it is not a dispatch cost:
that width never enters the worker (baseline and candidate both leave the
gate with 0 and run C's bigint_add_equal_fast inline in w_add). It pays the
new admission bit test (eight instructions, three predicted branches) plus
w_add's block movement, about 0.3 ns. It read 1.04-1.08 in every candidate
and 1.08 (0/31) when the test was folded into the exclusion block, so the
retained form is the cheapest measured. The width is outside the default
matrix; the default-matrix widths on the same C path pay only a `<= 24`
range exit and are at parity (add@32 1.009, add@64 0.983-1.008 across
rounds). A cheaper admission for the unported 5..23 widths would need a
different mechanism than a gate predicate (for example a width-indexed
seam table); it is left as the known cost of admitting five more widths.

SECOND TRANCHE — GENERIC EQUAL WIDTHS 5..7, 9..15, 17..23
=========================================================

Scope
-----

The widths between the fixed kernels have no straight-line C arm: C reaches
them through bigint_{add,sub}_equal_fast's `default:` case, which runs the
blocked bn_add_n / bn_sub_n loops. This tranche routes every positive
equal width from 2 through 24 to source:

  * add@5..7, add@9..15, add@17..23 — one generic raw leaf
    (`__bigint_add_equal_generic_raw(a, b, n)`): the hot take in C's class
    (the power of two above n: 8, 16, 32), the quad `adcs` loop
    (`asm_add_no`), and C's unconditional carry-limb publication through
    `w_bigint_add_equal_finish_raw(v, n, carry)`.
  * sub@5..7, sub@9..15 — one generic raw leaf
    (`__bigint_sub_equal_generic_raw(a, b, n)`): the top-limb compare with
    the full scan on a tie, the same class take, the quad `sbcs` loop
    (`asm_sub_no`), and the existing top-limb / trim-and-demote finisher.
  * sub@17..23 — the same leaf, but the kernel is a generated straight-line
    `sbcs` chain per width (four-limb groups in the fixed kernels' schedule
    plus a two- and/or one-limb remainder, no branches). With the quad loop
    these widths measured 1.05 (sub@20) and 1.08 (sub@23): its
    per-iteration overhead against C's 16-limb blocked loop.

The runtime gate's admission is now one range test per operator
(`sa == sb && 2 <= sa <= 24`, sub additionally `a != b`), cheaper than the
previous bit test, and the workers' equal-width blocks gain one
`5 <= an <= 23` arm after their fixed-width switches. Widths 25 and up,
negatives, mixed signs and `x - x` keep C.
