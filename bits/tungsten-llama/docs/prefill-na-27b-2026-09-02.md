# Qwen3.8-27B prefill on the Neural Accelerators, from a classic encoder — 2026-09-02

**Box:** Apple M5 Max (40 GPU cores), 128 GB, macOS 26.6. Engine
`scripts/bench/qwen38_mlx.w`; kernels `bits/tungsten-llama/lib/kernels/na/`
(unmodified — this is a wiring change). Measured 2026-09-03.

Follows `na-classic-encoder-2026-09-02.md` (the kernels and their three hard
rules) and `prefill-matmul2d-tuning-2026-08-27.md` (the tile tuning, and the
MTL4 integration this replaces).

Commits: `e23b29e4` (FFN in-batch), `0bfbf9db` (chunk 512), `1e60bd1b`
(attention + GDN).

## Headline

1984-token prompt, 64 generated tokens: **prefill 19.8 s -> 11.8 s, 1.68x**,
100 -> 169 tok/s, with **byte-identical generated ids** across every arm and
every rep. Best-observed runs; see the contention note below.

## What changed

### 1. The NA GEMM dispatches from the batch that is already open

`ffn_m4` reached `mpp::tensor_ops::matmul2d` through a Metal-4 argument table
on a separate MTL4 queue. `forward_multi` runs all 64 layers plus the lm_head
in ONE concurrent command buffer, so every MTL4 hop had to commit that buffer
and reopen it: **five blocking GPU round-trips per layer, 320 per chunk**, for
a measured ~4% end-to-end.

The `na/` kernels take plain `device` pointers and build their tensor views
in-shader, so they encode straight into the open batch. `ffn_na` is the two
f32->f16 stagings, three NA GEMMs, silu and the residual add — all in one
command buffer, ordered by scoped resource barriers. Every `metal4_*` object
(compiler, queue, allocator, pipeline, argument table) left the engine, and
with them the residency set that panicked the AGX driver on 2026-09-01.

`na_proj` rounds the row count UP to the M tile and dispatches exactly those
rows, rather than always paying `MULTI_MAX`. The cooperative-tensor store does
not clip, so what must be aligned is the tile grid; the scratch buffers are
already `MULTI_MAX` rows deep and `MULTI_MAX` is itself tile-aligned, so the
rounded width can never run off the end. At chunk 512 this is what keeps the
5-token parity fixture from paying 512 rows for 5 tokens.

### 2. The chunk went from 64 rows to 512

The chunk width IS the M of every prefill GEMM. The NA needs M >= 512 to reach
its ~53 TFLOPS plateau; crossover against the simdgroup ladder is M ~= 48-64.
At 64 the kernel was being run in the regime it barely wins in.

`PREFILL_CHUNK` (env, default 512) sets `MULTI_MAX` in gemm-prefill mode. It
must be 64 or a multiple of the 128-row NA tile — otherwise `na_proj` could
round a width past the scratch depth.

Two consequences fell out:

- **The simdgroup ladder tops out at 64 rows.** `nvfp4_gemm_f32`'s widest tile
  is MT=8 x 8 rows, and `multi_pipes` only carries keys for bw <= 64. Wider
  chunks therefore route to the NA in `enqueue_scaled_multi` /
  `enqueue_residual_multi`, rather than the ladder being extended.
- **`logits_multi` is sized by the VERIFY width (8), not `MULTI_MAX`.** At
  chunk 512 that buffer would have been 508 MB for eight rows of use.
  `forward_multi` now raises rather than overrun it.

`MAX_POS` is 2048 in gemm-prefill mode (640 elsewhere — the pair/triplet/quad
SDPA kernels hold their scores in threadgroup arrays sized 640). And
`decode_multi.metal`'s block-verify SDPA clamps `usable` to
`MULTI_MAX_DECODE_POS = 2051` and **silently drops the oldest positions past
that**, so `prompt + generate` is now checked against 2051 and RAISES. A
benchmark that truncates attention and still reports a plausible tok/s is
worse than one that stops.

### 3. Attention and gated-delta projections on the NA

q/k/v/o for the 16 full-attention layers and qkv/z/out for the 48 gated-delta
layers now run on matmul2d as well, so every NVFP4 projection in the model is
on the Neural Accelerators during prefill: 7 GEMMs per full-attention layer,
6 per gated-delta layer.

q, k and v read the SAME normalized activations, and so do qkv and z, so the
f32->f16 staging is hoisted out of the group: one conversion feeds two or three
GEMMs that then run concurrently, instead of each projection converting into a
shared buffer and serializing on it. The output projections need a residual add
— matmul2d has no accumulate-into-C mode — so they land in a scratch and
`residual_add` folds them into `x_multi`.

`na_stage` centralizes the staging and its two-sided fence: the LEADING barrier
is the WAR against the GEMM still reading the buffer, the trailing one the RAW
for the GEMMs about to read it.

## Measurements

1984-token prompt, 64 generated tokens:

```
prep_ids compiler/lib/lowering/calls.w 1984 ids_1984.json \
    ~/.cache/tungsten/qwen3.8-27b-mlx/tokenizer.json.bin
BIT_HOME=$PWD/bits M4_FFN=$m NA_ATTN=$a PREFILL_CHUNK=$c \
  bin/tungsten run scripts/bench/qwen38_mlx.w \
  mtp2 64 r2 mmap profile 1984 gemm-prefill multi auto ids_1984.json
```

The number is the `components: prefill=` wall-clock line — the whole prompt
phase, not just the GEMMs. (The per-chunk time also accumulates into the
`verify=` slot: `forward_multi` is the shared prefill/verify path.) Arms are
**interleaved inside each rep** so drifting background load lands on all of
them.

### Chunk 512 vs the 64-row baseline (5 reps)

| arm | chunk | FFN | attn + GDN | prefill ms, 5 runs | median | **min** | tok/s at min |
|---|---|---|---|---|---|---|---|
| legacy | 64 | ladder | ladder | 23605 19770 20092 24580 30158 | 23605 | **19770** | 100.4 |
| NA FFN | 64 | **NA** | ladder | 13764 13610 13752 16382 19717 | 13764 | **13610** | 145.8 |
| NA, `NA_ATTN=0` | 512 | **NA** | NA (per-projection staging) | 11899 11763 13864 13841 15583 | 13841 | **11763** | 168.7 |
| NA, `NA_ATTN=1` | 512 | **NA** | NA (shared staging) | 11885 11930 13894 15501 15610 | 13894 | **11885** | 166.9 |

Speedup vs legacy on min-of-runs: **1.45x** (NA FFN at chunk 64), **1.68x**
(chunk 512). Per-rep ratios against the legacy run of the *same* rep — the
statistic least sensitive to drifting load — give medians of 1.48x (n=8) and
1.78x / 1.66x (n=5).

### Chunk 64, three-way (3 reps)

This is the only width where the FFN-only / +attention split can be measured at
all, because the simdgroup ladder does not exist above 64 rows.

Reps 6-8 ran `legacy` / `NA FFN` / `NA FFN+attn` interleaved at chunk 64. The
`load` column is the 1-minute load average sampled right after each run:

| arm | FFN | attn + GDN | rep6 | rep7 | rep8 |
|---|---|---|---|---|---|
| legacy | ladder | ladder | 30877 (load 75) | 34082 (107) | 32978 (44) |
| NA FFN | **NA** | ladder | 17126 (77) | 26715 (79) | 26581 (40) |
| NA FFN+attn | **NA** | **NA** | 25107 (126) | 22567 (65) | 19610 (33) |

**Inconclusive, and the load column says why**: background load swung 33-126
*within* a single rep, which is the interleaving assumption breaking down. Over
every rep in which it ran, `NA FFN` is 1.48x legacy (per-rep median, n=8) and
`NA FFN+attn` is 1.51x (n=3) — indistinguishable. The reading to take is that
**moving attention to the NA is a wash at chunk 64**, which is what the kernel
table predicts: the attention projections are skinny (k/v are N=1024) and the
NA's crossover against the ladder is M ~= 48-64, so at M=64 those shapes have
nothing to gain. Attention on the NA pays at chunk 512 — where it is also the
only option.

## Reading the table

**"chunk 512, FFN only" is not a runnable arm.** `NA_ATTN=0` at chunk 512 does
not put attention back on the simdgroup ladder — the ladder physically cannot
do 512 rows — it only drops step 3's shared-staging optimization. The two
chunk-512 rows therefore measure that optimization, not FFN-vs-all, and they
land on top of each other (11763 vs 11885 min; 1.78x vs 1.66x per-rep median,
inside the noise). The f32->f16 conversions are small next to the GEMMs, so
hoisting them buys nothing at this scale; what mattered was step 2 routing
attention to the NA at all, which chunk 512 forces.

**Why 1984 and not 2000 tokens.** `MAX_POS` is 2048 and the block-verify SDPA
ceiling is 2051, so `prompt + generate <= 2048`. With 64 generated tokens 1984
is the longest prompt that fits — and it is arithmetic the engine now enforces
instead of truncating.

**Contention.** Another agent's SAT/multiprocessing workload was on the box
throughout; the 1-minute load average ran 66 -> 126 across the session and the
per-arm spread is 30-53%. Only one LLM engine process ran at a time (checked
before every launch). The legacy arm suffers disproportionately from CPU load —
it issues 31 chunks to chunk 512's 4, so it pays ~8x the host-side round-trips —
which means the median-based speedups are, if anything, generous to the NA and
the min-based ones are the conservative read. **A re-measure on a quiet box
would tighten every number here**; the id parity is unaffected.

## Toggles

| env | default | effect |
|---|---|---|
| `PREFILL_CHUNK` | 512 | gemm-prefill chunk width (= `MULTI_MAX`). 64, or a multiple of 128; anything else raises. |
| `M4_FFN` | 1 | 0 keeps the FFN on `nvfp4_gemm_f32`. Only meaningful at chunk 64. |
| `NA_ATTN` | 1 | 0 keeps the attention/GDN projections on the ladder. Only meaningful at chunk 64. |

`M4_FFN` keeps its name from the MTL4 era so existing A/B invocations still
work; there is no Metal-4 object left behind it.

## What is left

- **Fuse gate|up.** They share `global_scale` in every layer and read the same
  staged activations, so one NA GEMM at N = 2*FFN would halve that dispatch
  count and double its N-tile parallelism.
- **The chunk tail.** 1984 tokens at chunk 512 is 3x512 + 448, and the 448-row
  chunk still pays 512 rows of NA work.
- **Prefill is no longer GEMM-bound.** At ~11.8 s for 1984 tokens the rest is
  the gated-delta recurrence, the block-verify SDPA, RoPE/norms and cold weight
  streaming — none of which the NA touches. The next factor is there.
- **`ctx_hidden` is allocated unconditionally** at `MAX_POS * 5 * HIDDEN * 4` —
  210 MB at `MAX_POS = 2048` even when no drafter wants the taps.
- **Re-measure on a quiet box.**
