# MetaFlip scheduling and Core ML experiment

The [scheduler/allocation follow-up](PROFILE-SCHEDULER-2026-09-06.md) implements
and measures the next CPU/coordinator improvements. Core ML remains disabled.

## Outcome

Keep 16 CPU search workers on this 18-core host, GPU enabled, and Core ML off.
Do not reserve CPU cores for the measured model. The optional integration is an
experiment, not a throughput, search-quality, or record improvement.

MetaFlip's Bitfile now defaults its executable to `profile: "release", native:
true`. Previously ordinary `tungsten build` forced bit executables to `-O0`.
Explicit debug, CPU, target, and optimization overrides remain available.
The new default does **not** enable `--fast`.

## Host and method

- Apple M5 Max, 18 logical CPUs, 128 GiB RAM, macOS 26.6.2 (25G83).
- Isolated worktree based on `83f3737616c86a39b578e224cd80947641438fc3`.
- User's running fleet was paused by the user. Every measurement used a fresh
  state directory and bounded lifetime, with no other agent benchmark running.
- 5x5 GF(2), default exact rank-93 seed corpus, normal adaptive GPU portfolio,
  no TUI, 20 seconds per trial, first 5 seconds excluded from steady summaries.
- Two repetitions in forward/reverse order. These are short exploratory runs,
  not statistical proof of general performance differences.
- Every final tensor independently reconstructed and checked over GF(2).
  All 18 sweep runs exited successfully with healthy GPU status and no remaining
  child processes. No seed corpus, record ledger, or user checkpoint was changed.

`tools/bench_cpu_epochs.rb` records binary hash, full command/environment,
status snapshots, process CPU/RSS, system GPU utilization, coordinator phases,
model events and exact final-certificate hashes. OS CPU measurements exclude
exited macOS zombies whose time/RSS fields reset to zero. Phase wall occupancy
is not the same as CPU utilization; GPU utilization is system-wide.

## Why the CPU workers leave idle time

The inspected scheduler change `c37317c5` did not convert fleet workers to
fibers: `Thread.new` still reaches `w_thread_spawn_slots` and `pthread_create`.
Buffered channel polling's 100-microsecond sleep predates that change.

The fleet has synchronous batch boundaries: all CPU walkers finish, then one
coordinator performs controls, intake, archive/seed work, completed GPU harvest,
launching and status work before restarting the walkers. GPU harvest joins
controllers already known to be finished, not every live GPU kernel.

| CPU target epoch | Mean CPU moves/s | Main-process busy cores | Coordinator wall share |
|---|---:|---:|---:|
| 250 ms | 579.6M | 10.03 | 29.2% |
| 500 ms | 563.7M | 10.00 | 27.1% |
| 1,000 ms | 557.2M | 10.02 | 23.4% |
| 2,000 ms | 611.6M | 10.58 | 22.6% |

Longer epochs reduce coordinator share but increase barrier imbalance (roughly
4.1% to 9.8%). Replicate ranges overlap substantially. No cadence default was
changed. Asynchronous per-worker completion/dispatch and reducing coordinator
archive work are better next targets than increasing batch duration blindly.

The original build's counter sample reported about 4.07 instructions/cycle and
0.17 L1 data-load misses per thousand instructions in active code. Separate
release-build branch sampling reported approximately 1.26% branch misses;
partner selection dominated those misses. Backend-stall event counts were
concentrated in pressure-pair selection and slot removal. These samples do not
explain parked-worker time and do not establish a cache-stall bottleneck.

Counter traces used tungsten-flame's `rates`, `cache`, and `stalls` Instruments
templates, and its XML parser/sidemap tooling via `tools/analyze_profile.w`.
The installed Flame CLI's `--pid` path was a TODO, so recording used `xctrace
--attach` directly. Event aliases are platform-specific: notably the supplied
`LLC-load-misses` alias maps to `MMU_TABLE_WALK_DATA`, not a verified LLC-miss
counter. Do not infer LLC miss rates or stalled-cycle percentages from it.

## Core ML result

Training used 288 real, persisted, exact-verified escaped candidates from 12
origins, each labeled by 4,096 CPU moves. Origins and duplicate input basins were
kept together: six training, three validation, three test groups. Normalization
uses training data only. The 16-input MLP predicts rank-prioritized continuation
utility with a small term-turnover tie-breaker. Turnover is not archive coverage.

The 32/16 model and wider 128/64 and 256/128 variants, including 1x1 convolution
exports, were ANE-supported but CPU-preferred. The wider variants did not fix
placement and weakened held-out quality. A 5-second Core ML trace of 64 real
prediction batches had zero ANE interval rows, no target GPU work, and explicit
target CPU samples. **No Neural Engine acceleration was demonstrated.**

Actual Core ML FP16 scores were evaluated on all 72 held-out candidates, not
just the FP32 training reference. Maximum absolute score discrepancy was
0.0126944; the unrestricted top-quarter selections agreed. However, the
deployment-matched comparison was negative:

- Debt 1: learned selection's mean resulting rank was 93.2 versus heuristic
  93.0 (lower is better).
- Debt 2: both reached mean rank 93, but learned turnover was 0.16312 versus
  heuristic 0.16667.

The positive unrestricted turnover comparison mixed rank-93 controls with
escaped candidates and does not establish a benefit for the live lease policy.

### Concurrent allocation sweep

The model ran explicitly with `cpuOnly`, alongside CPU and Metal search. The
helper's worker setting means preprocessing concurrency, not core pinning or
ANE core allocation. Each model trial completed 9–10 batches, used 1–2 advised
seeds, and reported zero model/protocol failures.

| CPU search workers | Core ML host workers | Mean moves/s | Main busy cores | GPU utilization |
|---:|---:|---:|---:|---:|
| 16 | off | 595.6M | 10.17 | 98.9% |
| 16 | 1 | 507.9M | 8.60 | 98.2% |
| 15 | 1 | 448.8M | 8.51 | 98.6% |
| 14 | 2 | 482.1M | 8.95 | 98.8% |
| 12 | 4 | 456.3M | 7.75 | 98.7% |

Model advice changes search trajectories, so these differences are not a pure
measurement of inference overhead. Individual inference calls were generally
sub-millisecond. The measured quality and throughput do not justify enabling
this model or reserving cores for it. All final schemes remained rank 93.
